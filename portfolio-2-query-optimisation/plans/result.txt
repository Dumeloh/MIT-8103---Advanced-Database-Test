Q9 — Join Fan-Out Trap
  BEFORE Access Path : Hash Join (transactions × ledger_entries → 82,000 rows) +
                       Aggregate (double-counts every transfer amount)
  AFTER Access Path  : Index Only Scan on transactions only (join removed)
  Correctness Fix    : fan_out_total was ₦79,117,587.72 (2× inflated)
                       After fix: fan_out_total = correct_total = ₦39,558,793.86
  Key Lesson         : In double-entry ledger schemas, joining transactions to
                       ledger_entries for aggregation always doubles the result.
                       Pre-aggregate in a CTE or filter on direction = 'DEBIT'.

SECTION 5 — KEY DATABASE ENGINEERING PRINCIPLES DEMONSTRATED
────────────────────────────────────────────────────────────────────────────────

1. FOREIGN KEY INDEXING GAP (Q1, Q3, Q7)
   PostgreSQL does NOT automatically index FOREIGN KEY columns. Without
   idx_accounts_customer_id and idx_ledger_entries_transaction_id, every join
   on these FK columns triggers a full sequential scan. This is a critical
   production pitfall that caused Q3 and Q7 to run >1 second.

2. SORT ELIMINATION VIA B-TREE ORDERING (Q1, Q6)
   Matching the ORDER BY / DISTINCT ON key exactly to the B-Tree index column
   order (including DESC direction flags) allows PostgreSQL to eliminate Sort
   nodes entirely. For Q6, this also eliminated a 3,024 kB disk sort spill.

3. PARTIAL / FILTERED INDEXES (Q2, Q4, Q7, Q8)
   Defining indexes with WHERE clauses drastically reduces index tree size.
   The idx_ledger_entries_large_debits index covers only ~1.2% of all rows,
   making it 98.8% smaller than a full-column index while answering Q4 instantly.

4. COVERING INDEXES WITH INCLUDE (Q1, Q3, Q4, Q6)
   Including non-key columns in B-Tree leaf pages via INCLUDE enables Index-Only
   Scans — the engine never touches the table heap. Every INCLUDE-based index
   in this portfolio achieved 0 heap fetches.

5. THE NEGATIVE CONTROL LESSON (Q5)
   Q5's UNIQUE constraint auto-created transactions_idempotency_key_key B-Tree.
   Its 0.06 ms execution before and after proves: (a) UNIQUE constraints create
   automatic indexes; (b) FOREIGN KEY constraints do not — requiring manual DDL.

6. JOIN CARDINALITY & THE FAN-OUT TRAP (Q9)
   Joining a 1:N parent-child relationship (transactions : ledger_entries = 1:2)
   before aggregating doubles every transaction.amount in the SUM. This is a
   correctness bug, not a performance bug. The fix is architectural: remove the
   join or pre-aggregate the child table first.

7. WRITE AMPLIFICATION TRADE-OFF
   The 10 indexes add write overhead on INSERT into transactions/ledger_entries.
   Mitigation: ledger_entries is append-only (immutable financial history), so
   partial indexes targeting rare conditions (e.g., amount >= 4000) never trigger
   write amplification on ordinary small-amount transactions.
